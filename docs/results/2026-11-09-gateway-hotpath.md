# 网关热路径：定位—修改—对照

日期：2026-11-09。环境：本机 RTX 4080 Laptop GPU（12 GB）、WSL2 Ubuntu 26.04、vLLM 0.11.2、PyTorch 2.9.0+cu128；Qwen3-0.6B 与 Qwen3-1.7B 两个引擎同卡驻留。负载、提示、SLO 与网关限额沿用 R3/R4（seed 20261103，输入 64/1024 token，输出 16/128 token，到达率 1 与 8 req/s，网关并发 8、队列 16），账本放在 Linux 原生 ext4。结论只适用于本机单 GPU 的这组固定合成负载，不外推到集群或生产容量。

## 1. 问题

R3/R4 已测得：低负载下经网关比直连多等约 19 ms 首 token；云端经网关多等 23–26 ms，而上游 production-stack 路由只多 1.2–1.6 ms。R3 当时找到了“事件循环里同步写 SQLite”这一处，但没有拆清其他部分各占多少，改造一直暂缓。

## 2. 定位：逐请求阶段计时

网关给每个请求记录从到达起算的阶段时刻（`observation.phase_ms`）：到达记账、读完请求体、校验、版本绑定、就绪检查、分词、预约、写请求文件、拿到执行槽、二次就绪检查、派发记账、收到上游响应头、首个内容。代价是十几次 `time.monotonic()`，随请求写进账本。

基线网关在 0.6B、1 req/s 下（96 个请求的中位数，毫秒）：

| 阶段 | 内容 | 基线 |
|---|---|---:|
| 到达记账 | 1 次 FULL 提交 | 1.52 |
| 版本绑定 | 1 次 FULL 提交 | 1.06 |
| 就绪检查（第一次） | 哈希两个启动清单（在 Windows 挂载盘上）+ 读 `/proc` + HTTP `/health` | 5.79 |
| 分词 | chat template + tokenizer（线程池） | 0.95 |
| 预约 | 1 次 FULL 提交 | 1.18 |
| 写请求文件 | 请求体与 wire 输入 | 0.33 |
| 就绪检查（第二次，拿到执行槽后） | 同上 | 4.91 |
| 派发记账 | 1 次 FULL 提交 | 1.23 |
| 其余 | 读请求体、校验、拿槽 | 0.19 |
| **派发前合计** | | **17.2** |

两次就绪检查约 10.7 ms（62%），四次提交约 5.0 ms（29%）。其余三个负载层的构成相同。

## 3. 修改

**账本组提交。** 原来每个账本操作各自提交一次（WAL + `synchronous=FULL`，每次含 fsync），一个流式请求要提交 5 次（经发布控制器为 7 次），其中 4 次在派发之前，而且都在事件循环线程里执行。改为：每个操作是当前批量事务里的一个保存点，失败只回滚自身；COMMIT 只在持久化边界执行——派发到引擎之前（写前确认）、对外可见的结果之前（非流式响应、拒绝，以及流式响应的最后一帧）、清理结束时。一次 COMMIT 覆盖此前所有已执行的操作，并发请求自然共享；一个流式请求共 3 次提交，派发前只剩 1 次。`synchronous=FULL` 与派发前持久化不变；提交失败或批次被 SQLite 整体回滚时关闭写入并停止准入。代价：既没有派发、也没有响应的到达记录，可能随控制者崩溃丢失（有单元测试固定这一边界）。

**就绪检查分层。** 进程身份（PID、启动时刻、boot ID）仍然每个请求核对，同端口被替代实例接管时立即失败。清单哈希与 HTTP 健康探测改为后台每 0.2 秒执行一次，通过结果最多复用 0.5 秒，失败从不缓存，清单哈希放到线程里，不阻塞事件循环。第一版只做了“通过结果复用 0.25 秒”，没有后台探测，见第 5 节。远端 worker 的身份探测同样后台化，生成端的 `X-Expected-Worker` 栅栏仍逐请求拒绝错误代际。

**租约计数索引。** 副本池每次分配请求都要统计各副本、各版本未释放的租约，原来对 arrivals 整表扫描，代价随运行时间增长。增加两个部分索引（`WHERE lease_released=0`）。

## 4. 对照方法

`scripts/run_gateway_ab.py`：同一对引擎上，直连、基线网关、优化网关三条路径；稳态窗口在 3 次重复 × 2 个模型 × 2 个到达率上按全部排列轮换先后（36 个窗口、1,152 个请求）；发布窗口在两个网关上都做“别名请求 + 中途切换 active”（6 个窗口、384 个请求）。两个网关都从证据目录里的冻结源码副本启动，运行前核对导入路径，运行后核对源码未变。`scripts/report_gateway_ab.py` 从原始窗口事件重算全部统计，并逐条核对账本终态、清理证据、租约释放与 wire 输入 token。“额外等待”按输入逐条配对：同一提示经网关与直连的首 token 时间之差。

## 5. 结果

三轮 A/B 各自带一个基线网关：A 轮比较基线与第一版（只缓存通过结果 0.25 秒），B 轮比较基线与第二版（后台探测），C 轮在独立审查修复之后比较基线与最终代码。三轮各 1,536 个正式请求全部协议有效，各 42 个窗口调度有效。**对外引用以 C 轮（最终代码）为准。**

配对额外首 token 等待，中位数 / P95（毫秒）：

| 负载 | A 轮基线 | 第一版 | B 轮基线 | 第二版 | C 轮基线 | 最终代码 |
|---|---:|---:|---:|---:|---:|---:|
| 0.6B，1 req/s | 21.0 / 31.1 | 13.0 / 20.9 | 18.0 / 32.2 | 5.2 / 11.2 | 17.2 / 28.3 | **7.1 / 13.9** |
| 0.6B，8 req/s | 22.0 / 31.9 | 10.4 / 17.7 | 20.4 / 29.4 | 6.6 / 17.8 | 21.0 / 34.1 | **5.8 / 13.8** |
| 1.7B，1 req/s | 20.2 / 31.6 | 13.3 / 24.1 | 16.7 / 23.5 | 6.5 / 18.2 | 17.9 / 32.7 | **7.8 / 26.0** |

第一版在 1 req/s 时仍要做一次完整慢检查（第一次就绪检查 5.9 ms）：请求间隔约 1 秒，早已超过 0.25 秒的复用期，只有拿到执行槽后的第二次检查命中缓存（4.9 → 0.26 ms）。8 req/s 时两次都基本命中。这就是第二版改为后台探测的原因。

最终代码的中位额外等待比同轮基线低 56%–72%（第二版在 B 轮为 61%–71%）。三轮之间基线自身的波动约 ±2 ms，因此各轮之间的差异不再细分归因。派发前网关耗时（各阶段中位数之和，毫秒；B 轮）：

| 阶段 | B 轮基线（0.6B，1 req/s） | 第二版 |
|---|---:|---:|
| 到达记账 | 1.42 | 0.10 |
| 版本绑定 | 0.84 | 0.10 |
| 就绪检查（第一次） | 5.85 | 0.41 |
| 分词 | 1.11 | 0.96 |
| 预约 | 1.18 | 0.08 |
| 写请求文件 | 0.34 | 0.32 |
| 就绪检查（第二次） | 4.78 | 0.22 |
| 派发记账（第二版含唯一一次 COMMIT） | 1.23 | 1.49 |
| 其余 | 0.20 | 0.18 |
| **合计** | **16.96** | **3.85** |

其他两个负载层分别为 17.3 → 4.0 ms（0.6B，8 req/s）与 15.7 → 4.0 ms（1.7B，1 req/s）。C 轮最终代码的三层分别为 16.3 → 3.8、17.4 → 3.7、16.4 → 4.1 ms，与 B 轮一致。余下的约 4 ms 主要是派发前唯一一次 FULL 提交与分词；额外等待里另有约 1.5–2.5 ms 是多一跳 HTTP 转发与 SSE 逐事件解析。

**1.7B、8 req/s 处于过载**：32 个请求约 4 秒内到达，后半段请求的首 token 由排队主导，同样输入在不同窗口之间相差数百毫秒。A、B 两轮的 18 个此类窗口中，只有 B 轮第 2 次重复的优化网关窗口 SLO 达标 20/32，其余 17 个窗口均为 32/32 或 31/32（C 轮该层 9 个窗口全部 32/32）；该重复里三条路径同时变慢，vLLM 自报的 prefill 时间合计为 1.53–1.71 秒，其他重复为 1.29–1.35 秒，说明是引擎处理能力的波动，而不是网关在过载时变差。因此这一层不用于判断网关开销。

**发布窗口**：三轮共 18 个窗口全部 64/64 有效，实际版本与计划逐条一致，切换都在预留空档内完成。首 token 中位数：A 轮基线约 55.5 ms、第一版约 46.4 ms；B 轮基线 52.2–55.6 ms、第二版 40.1–45.3 ms；C 轮基线 49.5–53.1 ms、最终代码 36.9–39.6 ms。

副本池每次分配请求要对每个候选副本做这类计数；没有索引时，网关运行越久，每个请求的分配越慢。

## 6. 正确性

- 单元与合同测试：Windows 358 通过、3 跳过；Linux 361 通过。本轮新增 24 项，覆盖阶段计时、组提交的各条边界（保存点只回滚自身、写前确认、崩溃只丢失无对外效果的尾部、提交失败或批次被整体回滚后关闭写入、最后一帧之前终态已落盘、拒绝在响应前落盘、账本失败后仍归还容量并返回 503、启动失败也会关闭）、部分索引被查询计划使用，以及就绪缓存（并发共享、失败探测不排队、有效期从探测开始算、身份变化立即失效、后台探测时请求与副本池刷新都不等待探测、远端身份探测复用）。
- 真实故障回归（本机单 GPU，审查修复前后各跑一次，两次全部通过）：R2 两版本发布与故障矩阵 13 个阶段全部通过，离线审计通过（65 条到达，其中 1 条 unknown 是“控制者崩溃”阶段被强杀时的在途请求，重启后同一幂等键返回 409）；R1 单实例 14 类真实 TCP 场景全部通过（39 条到达，含取消后 KV 释放、过载、请求体与消息上限、三类期限、控制者恢复、worker 退出与换代重新绑定）。最终代码的原件在 `artifacts/r2-regress-20261109-final-*` 与 `artifacts/r1-regress-20261109-final-*`。
- 独立只读审查（B 轮之后）发现并已修复：失败的就绪探测会让等待者逐个排队重试，一个挂起的副本可拖住整个副本池；流的最后一帧先于终态落盘；只读语句出错导致批次被整体回滚时账本未察觉；异常下保存点深度可能卡住；账本失败后资源未归还、启动失败后探测任务未停。C 轮数字与下方故障回归都在修复后的最终代码上取得。

## 7. 边界

- 只测了本机单 GPU；云端双向 TLS 的远端 worker 路径同样改了，但没有重新上云测量。
- 0.5 秒的健康结果有效期意味着：引擎进程仍在但已挂起时，这段时间内的请求会被派发并等到期限（504），而不是立即得到 503。
- 剩余开销里约 1 ms 是派发前唯一一次 FULL 提交，约 1 ms 是分词；网关收到上游响应头之后的转发与 SSE 重组没有改。
- B 轮里优化网关的后台探测在整个测量期间一直运行（每个引擎每秒约 5 次 `/health`），也覆盖直连与基线网关的窗口；它对这些窗口的影响没有单独测量，按请求量估计可以忽略。
- 这是网关层的系统优化，不是推理引擎或 GPU 内核层面的贡献。
